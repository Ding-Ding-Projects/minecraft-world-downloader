Capture options

Downloading· Updated 13 August 2026· Applies to 1.4.0 and later

Three switches decide what the proxy writes alongside terrain. All three are on by default except Overwrite existing chunks, because overwriting is the only one of them that can lose data you already have.

OptionDefaultWhat it writes
Save entitiesOn Mobs, item frames, armour stands and their positions
Save block entitiesOn Chest contents, sign text, banner patterns, spawner data
Overwrite existing chunksOff Replaces chunks already on disk with the version just received
Failure modes

If the server sends a partial chunk packet the proxy re-requests it once and logs a retry line. If the retry also fails the chunk is skipped and named in the activity log — it is never written half-complete, because a truncated region file is harder to recover from than a missing one.

Overwriting is not undoable from local history. Region files are too large to snapshot, so history records that the setting changed but keeps no copy of the chunks. The confirmation gate says the same thing before you delete anything.
Security considerations

The proxy sees everything your client sees, including chat and inventory. Nothing is transmitted anywhere: every byte is written to the world folder you chose. Chat capture is a separate feature with its own switch, and it is off unless you start a profile.

Verifying it works

Start a download, walk about two hundred blocks, and stop. The activity log should name at least one written region file, and that file should exist in the world folder with a size greater than zero. Opening the world in a local client is the end-to-end check.

Every article ends with suggested articles. Related features, the prerequisite, and the natural next step, so a reader is never dropped at a dead end with no idea what to read next.

Each article covers behaviour, configuration, failure modes, security considerations and verification. Failure modes and verification are the two that get skipped, and they are the two a reader actually needs when something has gone wrong.

Docs are updated in the same task that changes behaviour. A fix that changes what a setting does edits the article that described the old behaviour, before the task is called complete. Stale documentation is worse than none, because it is confidently wrong and the reader has no way to tell.
