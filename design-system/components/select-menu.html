Selects and menus

The dropdown anatomy that every list-bearing control in this product uses — including the filter field and regex affordance that are mandatory in all of them.

Static design specimen. Every control below is a rendering of a state, laid out so the states can be compared side by side. Nothing on this page responds to input, and no element here is wired to behaviour — the state captions say which state each one shows.
Product-wide rule, not an option. Every dropdown, select, combobox, picker, autocomplete, menu button, overflow list and right-click menu in this product opens with a keyboard-focusable filter field at its head, and that field carries its own regular-expression builder affordance beside it. A four-item menu is not exempt: it grows to fourteen without anyone revisiting the decision, and a user who has learned to type in one dropdown and finds the next one inert has learned that the pattern is unreliable — which is worse than never having had it.

Keyboard first. The filter takes focus on open. Typing filters, arrow keys move through what survived, Enter activates, Escape clears the filter and only then closes the menu, and focus returns to the control that opened it. A screen reader gets the result count, not a list that silently shrinks.

Each field owns its own state. Query, pattern, flags, validation and mode belong to that one menu — never one shared builder that applies to whichever menu was opened last. Two menus open on one screen must not be able to contaminate each other.

Filtering must not hide a destructive item into invisibility while leaving its keyboard shortcut live. If Close tab is filtered out, the binding for it is filtered out too. Otherwise the shortcut fires against a menu that appears not to contain it.
