# World Downloader Studio — design system

Material Design 3 (M3 Expressive) design bundle for **World Downloader Studio**: a
Windows desktop application that combines four previously separate tools — a
Minecraft world downloader, a container/server manager, a live map viewer, and a
chat capture runner — plus its public documentation site.

Every file here is a **self-contained HTML specimen**. Open any one of them
directly in a browser with no network connection and it renders completely.

## What the token file is for

`foundations/tokens.css` is the **single source of colour, type, shape, elevation,
motion and spacing** for both implementations. The Electron application and the
documentation site each copy this file. Neither forks it, re-declares a token, nor
hard-codes a hex value that appears in it.

### The seed

The palette is generated from **`#0F7A3D`**, a deep grass green, chosen because the
product is about Minecraft terrain.

```
CIELAB   L* 44.7   C 49.7   h 149.1°
```

Six tonal palettes — primary, secondary, tertiary, neutral, neutral-variant and
error — are generated by holding hue and chroma and walking tone as CIELAB `L*`,
reducing chroma only where sRGB cannot hold it. This is the same construction M3's
HCT uses, where tone *is* `L*`. Because of that, tone 40 on one palette and tone 40
on another read as the same lightness, which is what makes a role swap consistent
across the whole system.

### The theming contract — the part that breaks silently

Every colour token is defined **once on bare `:root`**, which is the light theme.
Dark is then expressed **twice**, and both are required:

```css
:root { /* every colour token defined here */ }

@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) { /* only colour tokens redefined */ }
}

:root[data-theme="dark"] { /* the same redefinitions */ }
```

- The media query follows the operating system when the user has expressed no
  preference, and steps aside the moment they pick light explicitly.
- The attribute selector handles an explicit dark choice, which must win **on a
  light operating system too** — which is why it cannot live inside the media query.

**No token may have its only definition inside a media query or a `[data-theme]`
block.** A token that exists only in the dark block is undefined in light, renders
as an invalid value, and inherits or falls back to something arbitrary rather than
failing loudly.

Type, shape, elevation, motion and spacing tokens are theme-independent and are
declared once. They are never repeated in the dark blocks.

### Element-scoped themes are specimen-only

The specimen pages add `[data-theme="light"]` / `[data-theme="dark"]` blocks that
scope to any element, so light and dark panels can sit side by side on one page.
That block is clearly marked specimen-only. **Implementations copy `tokens.css`,
not that block.**

## Product-wide rules an implementer must not drop

These are not per-component decisions. They apply to **every user-facing surface in
both implementations**, including the documentation site and its own settings page.

### 1. Every search field has an anchored regex builder

Every search bar, filter field and settings search carries a regular-expression
builder **anchored to that specific field** — a popover attached to the field the
user is already typing in, never a distant menu or a global dialog. Plain text is
the default; regular expressions are an explicit opt-in. Query, pattern, flags,
validation and mode synchronize bidirectionally.

Where several search bars sit on one surface, **each gets its own builder** bound
to that field's own state. Never one shared builder that applies to whichever field
was touched last.

See `components/searchbar.html`.

### 2. Every dropdown and every context menu has a filter field

Every select, combobox, picker, autocomplete, menu button, overflow list and
right-click menu opens with a keyboard-focusable filter field at its head, and that
field carries its own regex affordance.

**"It only has four items" is not an exemption.** A four-item menu grows to
fourteen without anyone revisiting the decision, and a user who has learned to type
in one dropdown and finds the next one inert has learned that the pattern is
unreliable — which is worse than never having had it.

See `components/select-menu.html`.

### 3. Every rendered element supports *Edit appearance…* and *Lock this element…*

Both commands appear on every element's right-click menu with a keyboard
equivalent. Not a chosen subset of components — every button, field, label, icon,
row, card, menu item, tab, group, dialog, panel and notification.

The appearance editor is **non-modal and anchored beside the element being
edited**, tracks that anchor, and never covers the element it is changing. Each
lock carries **its own credential**; there is no master key and no inheritance.

See `app/appearance.html` and `app/locks.html`.

### 4. Every list has bulk actions

Multi-select with click and shift-click, a keyboard equivalent, a select-all that
**states plainly whether it means this page or every match**, and an inverse
selection. The notification centre and the history panel are lists too — "it is
only a log" is not an exemption.

Bulk actions show the exact count and a reviewable preview, distinguish "42
selected" from "42 will change" when some are skipped, and report what was excluded
and why.

See `components/table.html`.

### 5. Modal dialogs are for decisions the user must make before continuing

Confirmations, unsaved-changes prompts, destructive-action gates, credential and
consent steps. **That is the complete list.**

Everything that only informs becomes a corner-anchored, non-blocking toast.
Informational and success toasts auto-dismiss; **errors and warnings persist until
dismissed**. If the only button would be *OK*, it should not have been a dialog.

See `components/dialog.html` and `components/snackbar.html`.

### 6. No network assets, ever

No CDN script, no external stylesheet, no remote font, no remote image, no
analytics, no third-party request — in the application **and on the documentation
site**. Everything is bundled locally. Icons are inline SVG, never an icon font.

A documentation site that phones home while describing a privacy-respecting tool
undermines the claim it is making.

### 7. Emoji are decoration in dialogs and message boxes only

Never in a button, an action label, a field label, an accessible name, or any other
control text. In a control label an emoji lands in the accessible name, where a
screen reader announces it, and it renders as a different glyph on every platform.
Decorative emoji are marked `aria-hidden`.

### 8. Nothing clips, at any scale or in any language

Validate at 100/125/150/200 percent display scale, at narrow widths, and in
**bilingual mode where labels are longest**. Wide content — tables, code blocks,
diagrams — scrolls inside its own container; the page body never scrolls sideways.

### 9. Nobody ever pays

No purchase, no licence, no subscription, no trial that lapses, no feature held
behind an unlock. No nagging for payment, donations, sponsorship, reviews or
ratings — not as a toast, a banner, or a startup interruption.

### 10. Every state is a colour *and* something else

Selection is a container colour plus a check. Status is a colour plus a dot plus
text. Error is a border plus a label plus an icon plus supporting text. Every state
must survive a monochrome display and a red-green colour vision deficiency.

## Static previews

These are design artifacts. Component and pattern pages carry a banner stating that
the controls are renderings of states rather than live behaviour, and each state is
captioned with the state it shows.

Where an element stands in for something that cannot be included — a bundled
photograph, a real screen capture — it is drawn as a dashed or chequered region and
labelled **static preview** in the markup. Nothing is styled to look like a live
control without being labelled as one, and no fabricated image is presented as
evidence of a real surface.

## Verification applied to this bundle

- Every file's first line is its `@dsCard` marker.
- No file contains any `http://` or `https://` resource reference.
- No malformed hex values, and no `%%` escaping artifacts in emitted CSS.
- Every `on-` colour role clears 4.5:1 against its own container in both themes;
  most clear 7:1. The four roles that are deliberately below that — `outline`,
  `outline-variant`, `scrim`, `shadow` — are labelled *not a text pair* wherever
  they appear.
